# Verify the stories

## The promise

`apps/storybook` is a private workspace package that consumes `@solix/core` the way a consumer does, from its build and its stylesheet. Where the stories live is written once, in `apps/storybook/.storybook/main.ts`, and every check reads them from Storybook's own index of that configuration.

In each engine there are two stories projects, `stories` and `stories in the dark scheme`, inline projects of the root config made from the one list in `apps/storybook/tests/support/test-servers.ts`. Each provides its colour scheme as `storyColorScheme`, and its setup file sets it as `data-color-scheme` on `<html>` before each story, so every story runs, and passes its gates, in both schemes. Each stories project of `vp run verify` lists exactly the files of the stories in the index, as the test runner itself lists them for the run; every indexed story's tags pass the include, exclude and skip tags that Storybook's test plugin writes into that project's `env`; and the project narrows test names no further than the run does. A project whose `env` lacks one of the plugin's three tag variables fails by name rather than falling back to a default, and a run that lists no stories project, such as one filtered with `--project`, fails these checks first and says so.

The components the library exports are the exports of its built entry whose call signatures the type checker gives the return type a JSX element of this project has, compared by declaration. They are every built component, `SolixProvider` and `ColorSchemeScript`, and no other export, compared by identity; a source export the build lacks fails. Each is the component of the default export of at least one story file Storybook indexes, a static member that holds a part, such as `Grid.Col`, standing for the part, and the default export of every such file names a component. That those stories run is the listing check's to hold.

Every public prop of every exported component has, in the meta of each story file of that component, the control its type gives, and no argTypes of a meta or of an indexed story name a prop the component does not take or give a prop another control. A public prop is a property of the component's props, on any of its call signatures, declared in the library's source, whose type holds a value other than `undefined` and `null`; the attributes Solid's JSX types declare for the element are not, nor is a prop refused with `never` or `undefined`. `libraryComponentProps` in `scripts/component-props.ts` finds them through the checker, a type parameter such as a polymorphic `component` read as its constraint. A prop's control is a boolean for `boolean`, and a select of its type's literals when no string or number beside them is open (`string & {}` names the values to offer); else a text when a string is open, a number when a number is, an object when only an object is, and `control: false` for a function or an object with a method; `tests/rules/component-props.test.ts` holds each case on a probe component. The Vite plugin `storyControls` in `scripts/story-controls.ts` serves them as `argTypesOf` of `virtual:story-controls`, which each meta calls with its component and types with `satisfies ComponentMeta<typeof Component>` from `apps/storybook/story-meta.ts`, so the type checker refuses a meta whose controls are missing, written by hand or name a prop the component lacks, and a story typed `ComponentStory` that writes `argTypes`; the meta stays an object literal, since Storybook's indexer reads it statically, and the test holds what the types cannot tell; `main.ts` adds the plugin through `viteFinal`, so the dev server, the static build and the stories projects have it, and the root config adds it to the node project, whose tests import the stories. No story hides a control: `ComponentMeta` and `ComponentStory` refuse `parameters.controls`, and the test refuses a composed story that has controls parameters or composes a prop's argType to anything but what the generated argTypes compose to, so a `table.disable` or an `if` spread over `argTypesOf` fails. The controls add no arg: each indexed story, composed with Storybook's core annotations, has exactly the args its file writes, so every gate below runs a story on its own args, and a value picked in the controls panel is scanned by the accessibility panel there and by no gate.

The stories are each component's specification. Every own prop of a component is received by that component mounted in the canvas of one of its stories; the props every element component shares, those `ElementProps` adds, are shown once, in `apps/storybook/src/CommonProps.stories.tsx`, and keep their controls on every component. Every value of a prop whose type is a closed union of literals is received by a component mounted in a story's canvas, side by side in a story made by `everyValueOf` where the values look different, and every prop with behaviour, which its type tells, and every value of a closed one, is played: a mount in its story's canvas received it, the story passed, and its play function threw when the story ran again with another value read in its place at that mount, while the story passed as written in the run right before and right after; a story runs once more as written before its first substitution. Each run again ends at the story's own timeout, and one that does not end by then counts as failed, with an error that names the substitution, so a play that awaits a callback its no-op never calls plays that callback. The other value is the one its type gives: the next literal of a closed union, so the other boolean; a no-op for a callback, returning nothing or a no-op where it returns a callback, and an object of such no-ops for an object of callbacks; `null` where the type takes `null`. So a trivially true matcher plays nothing, an assertion that something is absent or a spy was not called plays what it checks, and `everyValueOf`'s own play plays nothing. The runs with a substitute happen in Chromium's light stories project only, to bound the time they take; the spec needs a record of every story from them. The dark project's runs credit nothing, so leaving them out takes no credit away; it only drops plays that would tell a value apart in the dark scheme alone, which then fail the spec. A mount counts only when a node it returned is inside the story context's `canvasElement`; a prop given as `undefined` is not received. Each control carries the prop's doc comment, from its one documented declaration, as its description, a style prop's from its table row, and no description for a prop with neither, since a prop needs no doc comment (Q163); and, as its default, the literal that the type of the `Defaults` its component merges into its props with `withDefaults` from `packages/core/src/parts.ts` gives, which only `defaultsOf<Props>()({ … })` makes, the one place a default comes from.

A story fails when its play function fails, when axe finds a violation of a rule that axe tags WCAG 2 A or AA and enables by default, target size included, after the play function, and when Solid's development build reports a diagnostic while the story renders or plays. After it ran, it fails when the page's `color-scheme` is not the scheme its project provides. It fails before it renders, and again after its play function, when its resolved accessibility parameters differ from the project's own or its resolved globals turn on `a11y.manual` or `ghostStories`, the globals the accessibility addon reads to skip its scan. Each story gets its own copy of its accessibility parameters, so a play function that writes to them does not reach the story after it. After its play function it also fails when its canvas holds `.sb-wrapper`, `#storybook-docs` or `#storybook-highlights-root`, the selectors the addon leaves out of its scan. A check parses the addon's built files and holds that they read exactly these globals and leave out exactly these selectors. In a development run it fails when Solid's development build is not loaded. axe leaves four rules that carry WCAG 2 A or AA tags out of a tag filter because it also tags them experimental; they do not run.

The broken stories in `apps/storybook/fixtures/Broken.stories.tsx` prove each gate bites: a button with no accessible name, two targets smaller than 24 pixels, a play function that expects the wrong text, an effect created outside an owner, an `onCleanup` called outside an owner, nine stories that try to leave the accessibility check: by `test: "off"`, `test: "todo"`, `disable`, their own `options`, their own `config`, the `manual` global and the `ghostStories` global before they render, by rendering inside `.sb-wrapper`, and by a play function that writes `test: "off"` after the check; and, right after that one, a link with no name, which fails on `link-name` only if the write did not reach it. Both Solid stories only report their diagnostic, so they fail through the gate and not because Solid throws. The last sets the other colour scheme on `<html>` in its play function, and fails for leaving its project's scheme. The broken-stories project runs in the dark scheme, so the page of every other broken story must end dark, which is not what a page with no scheme set would show. The stories project never collects them. In one run of all of them per engine, each fails for its own reason and for no other's. A reporter of the app's own writes each story's id, from the test's metadata, its status, each error's message and the `color-scheme` its page ended in, and the test finds each story's id in Storybook's index of the fixtures. The runner's default reporter runs beside it, so a failure outside a story has its cause in the output. The message matters because Firefox's and WebKit's stacks do not start with it.

The scripts of the package are the ones its tests run. Its static build succeeds. On each pull request, once `vp run verify` passes, CI uploads the build it made as the `storybook` artifact of the run, so people can look at every story. Served, in each engine, its sidebar lists every component of the build's story index, a story picked in the sidebar renders in the preview and its play function passes in the interactions panel, the accessibility panel reports no violation of it, a text arg typed into the controls panel reaches the preview, an option picked from the select the checker gives `Button`'s `variant` reaches the preview's button, the interface has `requestIdleCallback` and `cancelIdleCallback`, and the page raises no console error. Each engine runs these twice: as it is, and with both idle callbacks removed by an init script before the page loads, so the manager entry is exercised in every engine.

The app's manager entry, `apps/storybook/.storybook/manager.ts`, adds `requestIdleCallback` and `cancelIdleCallback` on a timer where the engine has none. Why it is there, and when it is reconsidered, is the revisit "Storybook's idle-callback workaround" in `ROADMAP.md`.

`core.disableTelemetry` in `apps/storybook/.storybook/main.ts` turns Storybook's telemetry off. The static build and the broken-story runs point `STORYBOOK_TELEMETRY_URL` at a collector of the tests' own, without `STORYBOOK_DISABLE_TELEMETRY`, and nothing arrives. The stories project inside `vp run verify` is not observed: its Vitest plugin sends its event while Vitest loads the configuration, before any setup can listen, and Storybook reads the endpoint once, when its telemetry module loads.

## The harm when it breaks

A component ships with no story, so no one sees its states and no gate runs on it. A prop has no control, or a control names a prop that is gone, so the panel no longer shows the component's specification. A control that adds an arg changes what every gate checks without any story saying so. A story that quietly leaves the run, or turns its accessibility check off, hides the regression it was written to catch. An accessibility regression, such as a control with no name or a target too small to hit, reaches users unnoticed. A reactive mistake that Solid reports only in development ships silently. A gate that stops biting turns every story green while checking nothing. Storybook's interface stops loading for the people who review components. A build reports usage to a third party without the owner's consent.

## Run it

```bash
vp test apps/storybook/tests packages/core/tests/component-exports.test.ts tests/rules/workspace-rules.test.ts
vp test --project "stories*"
```

The first line builds the library and runs the listing, coverage, broken-story, interface and interface-library checks. Run it without `--project`, so the listing holds every project. The second runs every story in each engine and scheme, against the library the first line built: a run of the stories projects alone builds nothing, so after a change to the library it checks the last build. With `CI` set, all three engines must be installed.

To look at the stories yourself, run `vp exec storybook dev --ci` in `apps/storybook`; the configuration keeps telemetry off there too.

## The tool and why

Storybook's Vitest addon turns each story into a Vitest browser test, so the stories run in the same runner and engines as every other browser test, and its accessibility addon runs axe after the play function. Storybook's own index and Vitest's own listing decide what runs, so no check repeats a glob. Solid's development build reports its diagnostics through `OBSERVE.diagnostics`, which a capture collects per story. No gate is trusted until the broken story for it fails, and the broken stories run through the same preview, so a gate that stops biting fails a test.

## What a pass covers

- Every story of the index in each installed engine, under the play, accessibility, settings and diagnostics gates.
- Every public prop of every exported component, with the control its type gives, in each story file's meta, no stale or changed control, and no arg a control adds.
- Every own prop received by its component mounted in a story's canvas, every shared prop by some component, every value of every closed union received, and every behaviour prop, and every value of a closed one, played: a play function that passes as written fails with the substitute its type gives, in Chromium, each with its description, where it has one, and its default in the controls.
- Each broken story in each installed engine, and that its failure names its own reason: `button-name`, `target-size`, the failed `toHaveTextContent`, `NO_OWNER_EFFECT`, `NO_OWNER_CLEANUP`, and, for the nine that try to leave the check, the setting they changed or the selector their canvas holds.
- The static build, its sidebar, one story with a play function picked in the sidebar, the interactions and accessibility panels for it, and console errors while doing so, in each installed engine.
- No telemetry from the static build or the broken-story runs.

## What a pass does not cover

- A value picked in the controls panel. No gate runs on it; the accessibility panel scans it there. A given shade or CSS colour from the `color` select may fall below its contrast, which is the consumer's to check; the palettes and variants the library chooses are held by `packages/core/tests/token-contrast.test.ts`.
- The part of a union that its one control cannot give. A text gives no number and no responsive object, so `size` takes a scale key or a CSS length in the panel but not a number of pixels; a number gives no string, so `GridCol`'s `span` takes a number but not `auto` or `content`; a select over the `string & {}` idiom offers its literals and no other string. `component` offers every tag Solid's `ValidComponent` takes, `area`, `base` and `script` among them, because which tag is sensible depends on where the component sits, inside an `svg`, a `map` or a list, and a narrower list would be one written by hand; it offers no component.
- A default the code does not give as a literal: a default that is a CSS token, such as `Button`'s `size`, or one computed, such as `GridCol`'s `span` through `withBase`, has none in the table.
- A description for every prop. A prop with no doc comment and no style-prop row has a control with no description; its name, type and default still show. No check asks a prop for a doc comment (Q163).
- What a doc comment says. One says only what the prop's name, type and default do not show, and no test reads that: pstack `no-comments`, step 3 of the `open-pull-request` skill, has the `comment-sicko` agent judge each comment a branch adds or keeps.
- A control for a function or an object with a method: it is listed with `control: false`.
- The four experimental WCAG 2 A and AA rules: `css-orientation-lock`, `p-as-heading`, `table-fake-caption` and `td-has-header`.
- Telemetry from the stories project inside `vp run verify`; see the promise.
- A pass-through a story throws away. A mount counts when a node it returned is in the canvas, so `SolixProvider`, which returns its children, counts wherever its children are shown; its behaviour props still have to play.
- Behaviour in Firefox and WebKit, and in the dark scheme. The substitutions run in Chromium's light stories project only; a play that tells a value apart only in another engine or in the dark scheme plays nothing, and a story that a run leaves changed only in the dark scheme is not run again there.
- A run again that runs out of time. It is not stopped, so its play may still be running beside the runs after it, and a play that passes, but only after the story's timeout, counts as failed and so plays the value.
- A cast to `Defaults`, or an `Object.assign` around what `defaultsOf` returns. Either can make the defaults the controls read from the type disagree with the values `withDefaults` merges at run time; no check refuses them.
- What a value does, beyond what the play reads of it. A play that only echoes a value back, such as `toHaveAttribute("aria-orientation", "vertical")` for `orientation`, fails with the other literal and so plays it, though it checks no keyboard behaviour; the substitution shows that the play reads the value, not that it checks the behaviour the value gives.
- Every other value. A value is played when its play tells it from the one substitute its type gives, the next literal, not from each other literal; a callback's no-op returns nothing, so a play that notices only a wrong return value of it notices nothing more.
- A story that a run leaves changed and the next run as written still passes: the runs as written before and after each substitution catch what fails them, not what they hide, and a play that passes or fails by how many times it ran before, such as one that fails only on its third run, can still be counted as played.
- A default that the library reaches other than through `withDefaults` and a literal fallback on a prop: a computed one, such as `Math.max(props.columns, 12)`, is not read as a fallback.
- That a story's play function ran to its end: a story is held to run, by the listing and the plugin's tags, not by a result of the run itself.
- Storybook's development server. Its interface is not driven.
- Every story in the interface. One story with a play function is opened there; every story runs as a test.
- Console warnings in the interface. Storybook warns about its own deprecated story store; only errors fail.
- Screenshots and visual changes. No baseline is kept.
- The upload itself. The check reads the workflow; only a pull request's run on GitHub uploads the build, so the artifact is first seen there.
- Keys that need trusted browser events, such as `Escape` on a modal dialog. The user-event of `storybook/test` dispatches events, so the playground's tests keep those.
- Firefox and WebKit where they are not installed.

## Reading a failure

- **The listing check says the run holds no stories project.** Run it without `--project`.
- **The listing check says a project's `env` holds no tag variable.** Storybook's test plugin renamed or dropped it; read its tag variables in `@storybook/addon-vitest` again.
- **The listing check names an engine.** The stories project does not run there what Storybook indexes: the root config lost the project, a file holds no story, a story lost the test tag, the plugin was given tags that leave a story out, or the project's config sets its own test name pattern.
- **`vp check` says a meta does not satisfy `ComponentMeta`, or `argTypes` does not exist in `Story`.** Give the meta `argTypes: argTypesOf(Component)` and write no other argTypes.
- **The controls test says the meta gives a prop no control.** Set the meta's `argTypes` to `argTypesOf(Component)` from `virtual:story-controls` with the meta's own component; if it already does, the plugin did not run: read `viteFinal` in `main.ts` and the root config's plugins.
- **The controls test names a prop that is no prop of the component, or a control its type does not give.** Remove the argType the story wrote, or change the prop's type, which is the spec.
- **The controls test says a story is given an arg its file does not write.** An argType carries an action or a default; remove it, or write the arg in the story.
- **The spec test says no story uses a prop, shows every value of one, or that no play failed with a value substituted.** Add the story it names: an arg or an attribute on the component, `everyValueOf(meta, "prop")` from `#/every-value.tsx`, or a play function that checks what the prop does, so the substitute its type gives fails it; a trivially true matcher does not.
- **The spec test says a story has no record from Chromium.** The run was filtered to other engines or to the dark scheme, or Chromium is not installed; the substitutions run in Chromium's light stories project.
- **The spec test says a behaviour prop is not playable.** Its type gives no substitute; give it a closed union, a callback type, or one that takes `null`.
- **A story fails because it failed as written when it ran again, before the first substitution or after one.** Its play or render leaves state, such as a module-level signal or storage, that the next run reads; reset it in the story's `beforeEach`. A shared prop may be shown in any story file; `CommonProps.stories.tsx` holds them.
- **The coverage test names an export.** Add a story file to `apps/storybook/src` whose default export names it, or the static member that holds it, as `component`.
- **A story fails on an axe rule.** The message names the rule and the element. Fix the component or the story; do not narrow the tags.
- **A story leaves the accessibility gate.** The message names the setting it changed. Remove it; fix what it hid.
- **A story fails on a Solid diagnostic.** The message names the code; read it in the `reactivity-diagnostics` skill.
- **A broken story passes, or fails for another reason.** A gate stopped biting, or the reasons crossed. Read the gate in `preview.ts` before anything else.
- **The interface test fails on the idle callbacks, in the run without them.** The manager entry no longer runs, or no longer adds one of them; a stuck accessibility panel or a console error on a changed arg follows from the same cause.
- **The accessibility-scan test fails.** The addon changed what it leaves out of its scan or which globals skip it; read its built files again and give `apps/storybook/accessibility-scan.ts` the new lists.
- **The interface test fails on a console error.** Read the stack: an error from a story's own module is a story problem, an error in Storybook's chunks after an upgrade is Storybook's.
- **The telemetry test lists a request.** `core.disableTelemetry` is gone or a script overrides it.
