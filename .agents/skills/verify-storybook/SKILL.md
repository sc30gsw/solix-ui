# Verify the stories

## The promise

`apps/storybook` is a private workspace package that consumes `@solix/core` the way a consumer does, from its build and its stylesheet. Where the stories live is written once, in `apps/storybook/.storybook/main.ts`, and every check reads them from Storybook's own index of that configuration.

In each engine there are two stories projects, `stories` and `stories in the dark scheme`, inline projects of the root config made from the one list in `apps/storybook/tests/support/test-servers.ts`. Each provides its colour scheme as `storyColorScheme`, and its setup file sets it as `data-color-scheme` on `<html>` before each story, so every story runs, and passes its gates, in both schemes. Each stories project of `vp run verify` lists exactly the files of the stories in the index, as the test runner itself lists them for the run; every indexed story's tags pass the include, exclude and skip tags that Storybook's test plugin writes into that project's `env`; and the project narrows test names no further than the run does. A project whose `env` lacks one of the plugin's three tag variables fails by name rather than falling back to a default, and a run that lists no stories project, such as one filtered with `--project`, fails these checks first and says so.

The components the library exports are the exports of its built entry whose call signatures the type checker gives the return type a JSX element of this project has, compared by declaration. They are every built component, `SolixProvider` and `ColorSchemeScript`, and no other export, compared by identity; a source export the build lacks fails. Each is the component of the default export of at least one story file Storybook indexes, a static member that holds a part, such as `Grid.Col`, standing for the part, and the default export of every such file names a component. That those stories run is the listing check's to hold.

A story fails when its play function fails, when axe finds a violation of a rule that axe tags WCAG 2 A or AA and enables by default, target size included, after the play function, and when Solid's development build reports a diagnostic while the story renders or plays. After it ran, it fails when the page's `color-scheme` is not the scheme its project provides. It fails before it renders, and again after its play function, when its resolved accessibility parameters differ from the project's own or its resolved globals turn on `a11y.manual` or `ghostStories`, the globals the accessibility addon reads to skip its scan. Each story gets its own copy of its accessibility parameters, so a play function that writes to them does not reach the story after it. After its play function it also fails when its canvas holds `.sb-wrapper`, `#storybook-docs` or `#storybook-highlights-root`, the selectors the addon leaves out of its scan. A check parses the addon's built files and holds that they read exactly these globals and leave out exactly these selectors. In a development run it fails when Solid's development build is not loaded. axe leaves four rules that carry WCAG 2 A or AA tags out of a tag filter because it also tags them experimental; they do not run.

The broken stories in `apps/storybook/fixtures/Broken.stories.tsx` prove each gate bites: a button with no accessible name, two targets smaller than 24 pixels, a play function that expects the wrong text, an effect created outside an owner, an `onCleanup` called outside an owner, nine stories that try to leave the accessibility check: by `test: "off"`, `test: "todo"`, `disable`, their own `options`, their own `config`, the `manual` global and the `ghostStories` global before they render, by rendering inside `.sb-wrapper`, and by a play function that writes `test: "off"` after the check; and, right after that one, a link with no name, which fails on `link-name` only if the write did not reach it. Both Solid stories only report their diagnostic, so they fail through the gate and not because Solid throws. The last sets the other colour scheme on `<html>` in its play function, and fails for leaving its project's scheme. The broken-stories project runs in the dark scheme, so the page of every other broken story must end dark, which is not what a page with no scheme set would show. The stories project never collects them. In one run of all of them per engine, each fails for its own reason and for no other's. A reporter of the app's own writes each story's id, from the test's metadata, its status, each error's message and the `color-scheme` its page ended in, and the test finds each story's id in Storybook's index of the fixtures. The runner's default reporter runs beside it, so a failure outside a story has its cause in the output. The message matters because Firefox's and WebKit's stacks do not start with it.

The scripts of the package are the ones its tests run. Its static build succeeds. On each pull request, once `vp run verify` passes, CI uploads the build it made as the `storybook` artifact of the run, so people can look at every story. Served, in each engine, its sidebar lists every component of the build's story index, a story picked in the sidebar renders in the preview and its play function passes in the interactions panel, the accessibility panel reports no violation of it, a text arg typed into the controls panel reaches the preview, the interface has `requestIdleCallback` and `cancelIdleCallback`, and the page raises no console error. Each engine runs these twice: as it is, and with both idle callbacks removed by an init script before the page loads, so the manager entry is exercised in every engine.

The app's manager entry, `apps/storybook/.storybook/manager.ts`, adds `requestIdleCallback` and `cancelIdleCallback` on a timer where the engine has none. Why it is there, and when it is reconsidered, is the revisit "Storybook's idle-callback workaround" in `ROADMAP.md`.

`core.disableTelemetry` in `apps/storybook/.storybook/main.ts` turns Storybook's telemetry off. The static build and the broken-story runs point `STORYBOOK_TELEMETRY_URL` at a collector of the tests' own, without `STORYBOOK_DISABLE_TELEMETRY`, and nothing arrives. The stories project inside `vp run verify` is not observed: its Vitest plugin sends its event while Vitest loads the configuration, before any setup can listen, and Storybook reads the endpoint once, when its telemetry module loads.

## The harm when it breaks

A component ships with no story, so no one sees its states and no gate runs on it. A story that quietly leaves the run, or turns its accessibility check off, hides the regression it was written to catch. An accessibility regression, such as a control with no name or a target too small to hit, reaches users unnoticed. A reactive mistake that Solid reports only in development ships silently. A gate that stops biting turns every story green while checking nothing. Storybook's interface stops loading for the people who review components. A build reports usage to a third party without the owner's consent.

## Run it

```bash
vp test apps/storybook/tests packages/core/tests/component-exports.test.ts tests/rules/workspace-rules.test.ts
vp test --project "stories*"
```

The first line builds the library and runs the listing, coverage, broken-story, interface and interface-library checks. Run it without `--project`, so the listing holds every project. The second runs every story in each engine and scheme, against the library the first line built: a run of the stories projects alone builds nothing, so after a change to the library it checks the last build. With `CI` set, all three engines must be installed.

To look at the stories yourself, run `vp exec storybook dev --ci` in `apps/storybook`; the configuration keeps telemetry off there too.

## The tool and why

Storybook's Vitest addon turns each story into a Vitest browser test, so the stories run in the same runner and engines as every other browser test, and its accessibility addon runs axe after the play function. Storybook's own index and Vitest's own listing decide what runs, so no check repeats a glob. Solid's development build reports its diagnostics through `OBSERVE.diagnostics`, which a capture collects per story. No gate is trusted until the broken story for it fails, and the broken stories run through the same preview, so a gate that stops biting fails a test.

## What a pass covers

- Every story of the index in each installed engine, under the play, accessibility, settings and diagnostics gates.
- Each broken story in each installed engine, and that its failure names its own reason: `button-name`, `target-size`, the failed `toHaveTextContent`, `NO_OWNER_EFFECT`, `NO_OWNER_CLEANUP`, and, for the nine that try to leave the check, the setting they changed or the selector their canvas holds.
- The static build, its sidebar, one story with a play function picked in the sidebar, the interactions and accessibility panels for it, and console errors while doing so, in each installed engine.
- No telemetry from the static build or the broken-story runs.

## What a pass does not cover

- The four experimental WCAG 2 A and AA rules: `css-orientation-lock`, `p-as-heading`, `table-fake-caption` and `td-has-header`.
- Telemetry from the stories project inside `vp run verify`; see the promise.
- That a story's play function ran to its end: a story is held to run, by the listing and the plugin's tags, not by a result of the run itself.
- Storybook's development server. Its interface is not driven.
- Every story in the interface. One story with a play function is opened there; every story runs as a test.
- Console warnings in the interface. Storybook warns about its own deprecated story store; only errors fail.
- Screenshots and visual changes. No baseline is kept.
- The upload itself. The check reads the workflow; only a pull request's run on GitHub uploads the build, so the artifact is first seen there.
- Keys that need trusted browser events, such as `Escape` on a modal dialog. The user-event of `storybook/test` dispatches events, so the playground's tests keep those.
- Firefox and WebKit where they are not installed.

## Reading a failure

- **The listing check says the run holds no stories project.** Run it without `--project`.
- **The listing check says a project's `env` holds no tag variable.** Storybook's test plugin renamed or dropped it; read its tag variables in `@storybook/addon-vitest` again.
- **The listing check names an engine.** The stories project does not run there what Storybook indexes: the root config lost the project, a file holds no story, a story lost the test tag, the plugin was given tags that leave a story out, or the project's config sets its own test name pattern.
- **The coverage test names an export.** Add a story file to `apps/storybook/src` whose default export names it, or the static member that holds it, as `component`.
- **A story fails on an axe rule.** The message names the rule and the element. Fix the component or the story; do not narrow the tags.
- **A story leaves the accessibility gate.** The message names the setting it changed. Remove it; fix what it hid.
- **A story fails on a Solid diagnostic.** The message names the code; read it in the `reactivity-diagnostics` skill.
- **A broken story passes, or fails for another reason.** A gate stopped biting, or the reasons crossed. Read the gate in `preview.ts` before anything else.
- **The interface test fails on the idle callbacks, in the run without them.** The manager entry no longer runs, or no longer adds one of them; a stuck accessibility panel or a console error on a changed arg follows from the same cause.
- **The accessibility-scan test fails.** The addon changed what it leaves out of its scan or which globals skip it; read its built files again and give `apps/storybook/accessibility-scan.ts` the new lists.
- **The interface test fails on a console error.** Read the stack: an error from a story's own module is a story problem, an error in Storybook's chunks after an upgrade is Storybook's.
- **The telemetry test lists a request.** `core.disableTelemetry` is gone or a script overrides it.

## When the change is intended

- A new component: add its story file. The coverage test fails until you do.
- A new gate: add a broken story for it to the fixtures and its reason to `reasonOf` in `broken-stories.test.ts`; the type of `reasonOf` makes you name one for every broken story.
- A new script in the Storybook package: run it under the collector in the interface test and add it to the scripts that test runs.
- Upgrading Storybook, its addons or its framework: run both lines above, then read the interface test's output in each engine CI runs.
- Mutation check after editing covered code: copy `preview.ts` first. Remove `test: "error"` from the project's accessibility parameters and run the broken-story test, which must fail for every broken story, `NoAccessibleName` and `TargetTooSmall` among them, with `a11y.test is "todo" where the project sets nothing`: the settings gate holds each story to the project's accessibility settings, and the addon's default is then `todo`. Then make the diagnostics check after each story return without throwing, which must fail it for the two Solid stories. Restore `preview.ts` from the copy and confirm with `cmp` against it.
