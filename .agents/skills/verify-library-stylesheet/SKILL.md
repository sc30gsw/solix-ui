# Verify the library stylesheet

## The promise

The stylesheet starts with one statement, `@layer ui-sdk, solix;`, which orders the behaviour SDK's layer before the library's, so every rule of the library beats every declaration of the SDK's that is not `!important`. Next, inside `ui-sdk`, comes the rule the SDK writes at run time to keep a hidden slot hidden, `display: none !important`, which the build reads from the SDK's package: a hidden part of a behaviour component stays hidden before hydration when a style prop, a consumer's class or a consumer's `style` without `!important` gives it a `display`. The build takes that rule only as one closed `@layer ui-sdk` block of one rule that declares nothing else, and otherwise fails. It adds to each of its selectors `:where()` of a class that starts with the stable class prefix, first in `class` or after a space, so the stylesheet alone hides no element of another library that carries a `data-slot`, one whose class holds the prefix inside a word included. Every rule the library build emits then sits inside the `solix` cascade layer, every class it emits starts with the library prefix, and every `!important` declaration of the stylesheet sits in `ui-sdk`. In the page, every rule the SDK adds at run time sits in `ui-sdk` too, its own hidden rule among them, which the narrowing does not reach. The last layer nested in `solix`, named `hidden`, holds one rule: an element that is `hidden` and has a class that starts with the stable class prefix is not displayed, so a hidden part with no slot, such as a `Box`, stays hidden before hydration when a class of the library's or a style prop sets `display`. The rule leaves an element that is hidden until found to the browser. The style-prop rules sit in the layer before it, named `style-props` and ordered after every layer StyleX emits, so a style prop beats a component default and still loses to a consumer's unlayered rule. Each style prop's rules come at its base and then at each breakpoint in ascending order. Every rule of a shorthand style prop, such as `p`, comes before every rule of a longhand it sets, such as `pt`, at every breakpoint, and the `hiddenFrom` and `visibleFrom` rules come after all of them. An alias has no rule of its own. Each `--sx-` custom property a style-prop rule reads is registered once with `@property`, `syntax: "*"` and `inherits: false`, inside the `style-props` layer. A registration applies to the whole page wherever it sits, so the layer only decides that a consumer's unlayered registration of the same name wins. The style-prop table that the build loads imports nothing at run time.

## The harm when it breaks

Without the order statement, the SDK's layer is declared after `solix` wherever its styles load after the library's, and a rule of the SDK's then beats the library's classes. Without the SDK's rule, a panel that the server renders `hidden` and that a consumer gives a `display` shows until the page hydrates; without the hidden layer's rule, so does a hidden `Box` that a style prop gives one. A hand copy of the SDK's rule drifts from the one the SDK writes at run time, and the page then hides a part before hydration by one rule and after it by another. Without the narrowing, importing the stylesheet hides every hidden element of another library that carries a `data-slot` and that its `style` gives a `display`; with a narrowing that finds the prefix inside a word, it hides one whose class merely holds the prefix; with the wrong prefix, it hides no part of the library's. With a hidden rule that also matches `hidden="until-found"`, the browser's find in page can no longer reveal such an element. A rule outside the layer, or an `!important` declaration inside it, beats the consumer's own CSS, so a consumer can no longer override that style with a plain class. A class without the prefix can collide with a consumer who also compiles StyleX. A style-prop layer ordered before a StyleX layer lets a component default beat the style prop the consumer passed, and a breakpoint emitted out of order lets a smaller breakpoint's value win on a wide screen. A shorthand rule emitted after a longhand's lets `p` at md undo `pt={0}`. A custom property that inherits lets `mt="unset"` take an ancestor `Box`'s margin. An import in the table that stays at run time stops `build.mjs` from loading it in plain Node.

## Run it

```bash
vp test packages/core/tests/stylesheet-properties.test.ts packages/core/tests/build-output.test.ts apps/playground/tests/behaviour-seam.test.ts
```

It takes about ten seconds with one engine installed. The first file is the generated check. The second checks the stylesheet that the real library sources build to, including that the SDK's rule comes from the SDK's package, that the build refuses a malformed one, that every `!important` declaration sits in `ui-sdk`, the nested-layer order, the order of the breakpoint rules against the owner's breakpoints, `ownerBreakpoints` in that file, the order of shorthand rules before longhand rules, the `@property` registrations, the aliases, and that the built table imports nothing. The third opens the built playground in each installed engine and reads what the hidden rule, the rules the SDK adds and the layer order do there.

## The tool and why

No verifier runs on a JavaScript build script, so this is not a proof. `stylesheet-properties.test.ts` uses fast-check to generate style definitions and runs each through the real `compileLibrarySource` and `libraryStylesheet`, then parses the result with PostCSS. Nothing is modelled by hand.

## What a pass covers

- `generatedRuns` generated definitions per run, as `stylesheet-properties.test.ts` sets it, a different set each run.
- Style namespaces whose properties come from `valuesByProperty` in that file, its CSS properties and the two private custom properties, and sometimes a `::backdrop` block of properties with plain values, each as many as the generator there draws.
- Values that are plain, or conditional on pseudo-classes (including `:user-invalid` and `:disabled`), `data-*` attribute selectors, the `open` attribute, `@media`, `@supports`, and `stylex.when.ancestor`, `siblingBefore` and `descendant`, nested as deep as the generator allows.
- For each of those definitions, that the stylesheet starts with the order statement and then the SDK's rule, that no declaration in `solix` is `!important`, and that the style-prop layer and then the hidden layer are the last two layers nested in `solix`, whatever layers StyleX emits for it, and that every `@property` registration carries the library prefix. `@property` is a global rule, not a class, so the tests that walk classes leave it alone, and the test that says what the `style-props` layer holds allows it next to the classes and the media blocks.

## What a pass does not cover

- `stylex.keyframes`, `stylex.createTheme`, pseudo-elements other than `::backdrop`, conditions inside a `::backdrop` block, and styles whose values are only known at run time.
- The browser's cascade itself. That an unlayered rule beats a layered one comes from the CSS specification; `apps/playground/tests/button.test.ts` and `apps/playground/tests/box.test.ts` check it in each installed engine for a few cases.
- A consumer who puts their own CSS in a layer declared before `solix`. That consumer loses to the library.
- A consumer who names `solix` in a layer order of its own before the library's stylesheet, or imports the stylesheet into a layer. That consumer decides where `ui-sdk` falls, and `packages/core/README.md` says to name it before `solix`.
- A hidden part with no slot whose consumer class or `style` sets `display`, such as a `Box`. The hidden layer's rule loses to it, as every rule of the library does. A part with a slot is hidden by the SDK's rule instead.
- `!important` in generated definitions. The generator never writes it, so only the real sources are checked for it.

## Reading a failure

- **An `expect` fails.** This is a real break. fast-check prints the smallest definition that triggers it under `Counterexample`, with a `seed` and `path`. Report it in these terms: which definition, and which rule left the layer or lost the prefix. Do not loosen the assertion.
- **`BABEL_TRANSFORM_ERROR` from StyleX.** The generator wrote source that StyleX rejects, so the check never ran for that input. Fix the generator in `stylesheet-properties.test.ts`, as `withoutRepeatedConditions` does for a condition nested inside itself.
- To replay one failure, add the printed `seed` and `path` to the options object passed to `fc.assert`, run again, and remove them afterwards.

## When the change is intended

- Renaming the layer or the prefix: change the constant in `build-pipeline.mjs`. The tests import it, so they follow.
- Adding a second top-level layer, or emitting rules outside the layer on purpose: this changes the contract in `AGENTS.md`. Change that rule first, then the assertion on the stylesheet's top-level nodes.
- Changing a breakpoint: the owner fixed them. Change the table in `packages/core/src/style-prop-table.ts` and `ownerBreakpoints` in `build-output.test.ts` together. `apps/playground/tests/box.test.ts` and `drive.mjs` read the widths from the table.
- A new shorthand style prop: give each of its longhand rows `within` naming it. If its CSS property is not one `longhandsSetBy` knows, add the longhands it sets there, from the CSS specification.
- Upgrading StyleX: change the version in the catalog in `pnpm-workspace.yaml`, then run the check.
- Upgrading the SDK: if the build fails in `behaviourSdkHiddenRule`, find where the new version writes its hidden rule, point `sdkHiddenRuleSource` at it, and run the check; `behaviour-seam.test.ts` fails if the rule the SDK writes at run time differs from the one the build read.
- Using a StyleX feature listed under "does not cover": add it to the generator first.
