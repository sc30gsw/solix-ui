# @solix/core

The components of Solix UI, a component library for Solid 2.0. The components are written in StyleX and ship as JSX source with their styles compiled to plain class names and one stylesheet, so a consumer needs no StyleX build setup. The headless layer is the platform where it has one: a disclosure is a `<details>`, a modal is a `<dialog>`. `Tabs` takes it from UI SDK.

## Build it

From the repository root, with the Vite+ CLI (`vp`). Without a global `vp`, put `pnpm exec` in front of each command.

```bash
vp install
```

```bash
vp run -r build
```

`build.mjs` runs Babel with the StyleX plugin through `build-pipeline.mjs` and writes `dist/*.jsx` (StyleX compiled away, JSX kept) and `dist/styles.css` (the layer order, the SDK's hidden rule inside `@layer ui-sdk`, then every other rule inside `@layer solix`). A consumer imports the components from `@solix/core` and the stylesheet from `@solix/core/styles.css`.

`vp test` builds the library and the apps in `apps` in production mode before it runs any test. `tests/build-output.test.ts` and `tests/style-prop-output.test.ts` check what the library build writes, `tests/stylesheet-properties.test.ts` checks the build pipeline on generated style definitions, `tests/component-contract.test.tsx` checks the root contract, the style props and the parts of every exported component, `tests/box.test.tsx` checks `Box` against fixed cases written from the requirement, and `tests/token-contrast.test.ts` checks how each token is written and the WCAG contrast of the colour pairs in each component's `stylex.create` blocks. What a consumer sees in a browser is checked in `apps/playground/tests`.

## How it is built

- It ships JSX source under a `solid` export condition. This is the library model the Solid Vite plugin documents.
- Each component's `stylex.create` block compiles to plain class strings at build time. `createParts` in `src/parts.ts` calls `stylex.attrs` at run time. No other file in `src` calls `stylex.attrs` or `stylex.props`, and `tests/rules/library-modules.test.ts` at the repository root checks it.
- Every component, `Box` included, gets the props of its root and of each other part from one `createParts` call, so it takes every style prop and every prop that hides it, such as `hiddenFrom` and `lightHidden`, with no code of its own, except `Modal`, below. Its root carries one stable class, `solix-<Component>-root`, unless `component` names another component. Each component exports its props type, such as `ButtonProps<T>` or `DisclosureProps`, for a wrapper to use.
- A component takes `component` when its job does not depend on one element, as `Box` and `Button` do, and renders that element through `dynamic()`. A component whose behaviour belongs to one element, such as `details`, `dialog` or `input`, does not take it and renders that element itself. Given a component as `component`, `Box` and `Button` take that component's props, and their type refuses a style prop that component's type declares `never`. At run time they resolve every style prop they are given, display ones included, into classes and custom properties for that component's root, and they pass it `classes`, `styles` and `unstyled` as well as applying them to their own root.
- Every component takes `classes` and `styles`, keyed by its parts, and `unstyled`. Its parts are the keys of its `stylex.create` block, `root` among them, and each part carries the stable class `solix-<Component>-<part>`. A class that `classes` names for a part beats the library's style on that part, as a plain `class` does on the root. A declaration that `styles` names for a part is written inline on it, and on the root the consumer's `style` beats `styles.root`. A declaration whose value is `undefined` or `null`, in `styles` or in `style`, sets nothing and replaces nothing. `unstyled` drops the library's look from every part and keeps the stable classes, the style props, `classes`, `styles`, `class` and `style`.
- `Modal` takes no display prop: `display` and each prop that hides an element, which `displayPropNames` in `src/style-prop-table.ts` lists. A class that sets `display` on a `<dialog>` beats the browser's own hiding of a closed dialog, so a closed modal would show on the page. Its type declares each of them `never`, and it leaves them out of its style props at run time too. A `Box` or `Button` that wraps `Modal` refuses them by its type only: given them anyway, it resolves them into classes on the `<dialog>`. It passes a consumer's `ref` the `<dialog>` along with its own.
- A component with behaviour, such as `Tabs`, gives its `createParts` call to `bind` on a behaviour, with the slot of the SDK each part takes. `createBehaviour` in `src/headless.ts` makes the behaviour from a primitive of the SDK, and that file is the only one that imports the SDK. A part bound to a slot keeps its own element, class and style, and takes the slot's role, ARIA attributes, handlers and ref; an event reaches the handlers in the order `AGENTS.md` states. `partId` there builds the id of a part from the root's `id` and a value, so a value with a space still gives an id that `aria-controls` can name.
- It compiles with its own class name prefix, `sx`, so its classes cannot collide with a consumer who also uses StyleX.
- A consumer who compiles StyleX passes `stylex.attrs(styles.name).class` through `class` or `classes`, and it beats the library's style, as a plain class does. A `SolixProvider` whose theme's `primaryColor` names another palette, scoped to a wrapper by `cssVariablesSelector`, themes the components inside it; under nested providers the nearest one's primary wins, on its wrapper and in every scheme island inside it. A `primaryColor` that names no palette, or the primary itself, leaves the primary as it was, and in the browser Solid's development build warns of it. `apps/stylex-consumer` builds with the StyleX Vite plugin, whose output is unlayered, and its tests check all three in each installed engine, with the library's stylesheet before the consumer's and after it.
- Its peers are Solid, StyleX and `@solix/primitives`, whose `createUncontrolled` holds the selected tab whether the app controls it or not. A consumer installs `@solix/core` and `@solix/primitives`, and one who also uses the primitives directly gets one copy of them. Beyond its peers it has the runtime dependencies `scripts/runtime-dependencies.json` allows, each with its reason. They install with the library, a consumer lists none of them and needs no build setup for them, and an app that renders only `Button` bundles none of their code. The disclosure needs no JavaScript: it opens and closes with scripts turned off.
- A style prop, such as `mt="md"` on `Box` or any other component, writes only the custom property `--sx-mt` into `style`. The class `sx-mt` in `solix.style-props`, ordered after `solix.components`, which holds the StyleX layers, reads it, so a style prop beats a component default and loses to a consumer's plain class and `style`. `hiddenFrom` and `visibleFrom` sit in the same layer, so a consumer's class that sets `display` beats them too. `lightHidden` and `darkHidden` sit in `solix.color-scheme`, the next layer, and lose to a consumer's class the same way. They hide an element in the scheme of the nearest ancestor that carries `data-color-scheme`, light where none does: each scheme sets an inherited custom property that the prop's class reads into `display`, as `none` or as `revert-layer`, which leaves the `display` to the layers before, so an element that is shown keeps its own.
- The props, their CSS properties, the breakpoints and the class prefix are one table in `src/style-prop-table.ts`, which imports at run time only the layer registry in `src/layers.ts`, which imports nothing. A component's own variables sit beside it in `src/Component.variables.ts`, which imports only `defineVariables` from that table. `build.mjs` loads the build of the table and of every variables module and writes the rules from them. `src/style-props.ts` turns a component's props into its style-prop classes and custom properties.
- A style prop drops `null` and any value that holds `;`, `{` or `}`. `tests/component-contract.test.tsx` draws such values among the generated ones and checks that none of them reaches the `style` attribute, and that `style` holds nothing but the custom properties the given style props' classes read and the consumer's own declarations.
- Each `--sx-` custom property is registered with `@property` and `inherits: false`, inside the `style-props` layer. A registration applies to the whole page, and a consumer's own unlayered registration of the same name would win. So `mt="unset"`, another CSS-wide keyword or a value the browser rejects leaves the margin unset instead of taking an ancestor `Box`'s `mt`.
- The stylesheet starts with `@layer ui-sdk, solix;`, so every rule of the library beats the SDK's rules, which sit in `ui-sdk`, except the SDK's `!important` declarations. A consumer who orders layers itself, by naming `solix` in an `@layer` statement before the library's stylesheet or by importing the stylesheet into a layer, decides where `ui-sdk` falls, and names `ui-sdk` before `solix`, or before the layer it imports into.
- Next, inside `ui-sdk`, it holds the rule the SDK writes at run time to keep a hidden part of a behaviour component hidden, `display: none !important` on a hidden element with a `data-slot`, narrowed to an element whose `class` starts with the stable class prefix, `solix-`, or holds it after a space. `build.mjs` reads that rule from the SDK's package and adds the narrowing through `:where()`, so it adds no specificity. The server's markup is hidden by it before any script runs, when a style prop, a consumer's class or a consumer's `style` without `!important` gives the part a `display`, and an element of another library with a `data-slot` is left alone, one whose class holds `solix-` inside a word included. Once a behaviour component hydrates, the SDK adds its own rule, which reaches every hidden element with a `data-slot` on the page.
- The last layer inside `solix`, `hidden`, hides a `hidden` element whose `class` starts with the stable class prefix or holds it after a space, so a part with no slot, such as a `Box`, that is hidden stays hidden when a class of the library's or a style prop gives it a `display`. It leaves an element with `hidden="until-found"` to the browser. A consumer's own class or `style` that sets `display` on such a part beats that rule, as it beats every rule of the library.
- The rules come in order of shorthand depth, then breakpoint: every `m` rule, then every `mx` and `my` rule, then every `mt`, `mb`, `ml`, `mr`, `ms` and `me` rule. So `<Box p={{ base: "xs", md: "lg" }} pt={0}>` keeps its top padding at 0 at md and above.
- A component's own props that set its layout, such as the minimum size `Space` takes from `h` and `w`, are its variables: rows that its `Component.variables.ts` gives `defineVariables` from `src/variables.ts`, under the name of the component that owns them. The component names, in the `variables` option of its `createParts` call, the prop or the function of its props that gives each variable of its group, and the type of that option requires every one. `createParts` keeps the props it names off the root and turns each value into an `sx-` class and the `--sx-` custom property it reads, the same way as a style prop, at its base and, for a responsive row, at each breakpoint. Each row sets the custom property named for it, such as `--space-min-height`, which the component's own styles read. A row may carry child rules, which style the children of the element that carries its class, or the children of a child they name, from a layer nested first in `style-props`, so a style prop on a child still beats them, and `unstyled` drops them.
- A responsive variable can follow a container's width instead of the viewport's, as `SimpleGrid` does with `type="container"`. Its values are then keyed by container widths, such as `"30em"`, which no stylesheet can know in advance, or by breakpoints, whose widths are the library's, the ones the style props use, applied to the container and written in `rem`, so a breakpoint is the same width in a container query as in a media query, whatever the container's font size. A `Grid` with `type="container"` and no `breakpoints` uses those widths too. A media query is never the fallback. The component renders its root inside its `container` part, an element with `container-type: inline-size`. It, and each member that keys a value by one of its widths, such as a `Grid.Col`, renders its own `<style>` before its own element, with the rules for the variables it places, so no `<style>` waits for another component's props while the page streams. A column leaves out a rule an earlier column of its grid already wrote, so twelve like columns write each rule once, and a column that streams in later writes only what none before it wrote. When an earlier column has not settled yet, a later one writes the rule too, and the copy does no harm. The `<style>` carries `data-solix-rules`, starts with the stylesheet's layer order, `@layer ui-sdk, solix;` and then the library's sub-layers, `components`, `style-props`, `color-scheme`, `container-queries` and `hidden`, and puts its rules in `@layer solix.container-queries`, which ranks after `style-props`, so a page that links the stylesheet after its markup ranks them the same. Its classes carry a scope from `createUniqueId`, so two grids on one page, one nested in the other, take nothing from each other. The rules hold only class names, property names and each width the type of the prop accepts, written back as a number and its unit, and no other value a consumer gives.
- A compound component's member reads what it needs from its carrier through a context. `Grid` passes its `classes.col` and `styles.col` to each `Grid.Col` that way, and the column puts them before its own `classes.root` and `styles.root`, so a column's own value wins.
- `mis`, `mie`, `pis` and `pie` are aliases of `ms`, `me`, `ps` and `pe`. Each pair sets the same custom property and class, so the stylesheet holds their rules once.
- Its tokens are the CSS custom properties `--solix-*` in `src/tokens.stylex.ts`. A colour token is written `light-dark(<light>, <dark>)`, each value in OKLCH. A shadow token is a list of shadows, each of lengths in rem and an OKLCH colour. Every other token is a length in rem, so it measures the same wherever it is used. The font sizes and line heights hold the heading sizes `h1` to `h6` beside `xs` to `xl`, so `fz="h1"` takes the first heading's size, and a theme sets the shadows under `shadows`.
- The colour scheme is the attribute `data-color-scheme`, `light`, `dark` or `auto`, on any element. The build writes no `light-dark()`: each colour token's default is its light value, and an element with the attribute sets every colour token to the value of its scheme, and `color-scheme` with it, so native controls follow; `auto` follows `prefers-color-scheme` with no script. A build tool that lowers `light-dark()`, as Vite's minifier does for its default targets, would otherwise resolve every token at `:root`, and a scheme set on an inner element would not reach the tokens. With no attribute the scheme is light. Since an element with the attribute sets every colour token itself, a consumer who overrides a colour token on `:root` and nests schemes sets the override on `[data-color-scheme]` too.
- `SolixProvider` takes `defaultColorScheme` (`light` unless given), `forceColorScheme`, `colorSchemeManager` (one `localStorageColorSchemeManager()` for the page unless given) and `getRootElement` (`<html>` unless given), which it reads tracked, so the accessor of a signal serves an element that mounts later. After hydration it reads its manager and then writes the computed scheme, `auto` resolved, on the root element. While nothing is stored it follows its default, and it follows the system and its manager. On the server it writes nothing, so a server-rendered page hydrates without a mismatch. Under `forceColorScheme` its controls do nothing; it still follows its manager, so it gives the stored scheme as soon as the force is lifted. A provider inside another owns a scheme only when it is given `getRootElement`: without it, it passes on the scheme of the provider around it, as it does the nonce, and a scheme prop it is given throws. A manager is `get()`, which gives the stored scheme or `undefined`, `set(value)`, `clear()` and `subscribe(onUpdate)`, which returns its teardown; it tells every subscriber of a set and of a clear, the clear as `undefined`, its own and, for the one in local storage, another page's. `createColorScheme()` gives `colorScheme`, `setColorScheme`, `toggleColorScheme` and `clearColorScheme`, and `createComputedColorScheme()` the scheme `auto` resolves to.
- `ColorSchemeScript`, rendered in `<head>`, sets the stored scheme on `<html>` before the first paint, or the default when nothing is stored or the storage throws, as the provider does after it. It carries the nonce of the provider around it unless it is given its own, so a page with a separate nonce for scripts passes that one as `nonce`. The app writes `data-color-scheme` on `<html>` itself, as the playground's `src/Document.tsx` does, so the page has its scheme with scripts off too.
- The library paints no page background. No selector of its stylesheet, of a `<style>` a component renders, or of the provider's under its default selector, `:root`, has an element type as its subject, so no rule selects `<body>` or `<html>` by its type, and a rule that needs no class, such as the token defaults on `:root`, declares only custom properties and `color-scheme`; `tests/page-rules.ts` reads both from every selector. An app paints the page itself with the tokens, `background-color: var(--solix-color-body)` and `color: var(--solix-color-text)` on `<body>`, as the playground's `src/app.css` does. Until it does, a page with the scheme on `<html>` shows the browser's own page colours for that scheme, not the tokens.
- A component that takes `color`, `variant` and `autoContrast` types them `ColorProps<Variant>`, with `Variant` the variants of the table it offers, and passes `{ color: { variants: [...], default: <its default variant> } }` to `createParts`, which refuses by type props whose `variant` takes one the list leaves out; a `variant` the list does not hold, given at run time, falls back to the default. A component without the `color` option may have a `variant` of its own. The `color` option sits beside `keep`, the props it keeps off the root, and `variables`, and reads the four slots of `variantColors` in `src/variant-colors.stylex.ts`: background, hover, colour and border. The palettes, the shades `0` to `9` and `contrast`, and the primary and the alias `orange` are the lists of `src/color-table.ts`. The build compiles one class per palette, which sets the shades, and one rule per variant of the variant table, on `data-variant`, so naming a palette writes nothing at run time. A shade such as `red.3`, or a CSS colour, writes one custom property, `--solixc-color`, which every variant reads where the table says: `filled` paints it solid and hovers 90% of it toward its text, `light` tints with 15% of it and hovers with 20%, `outline` draws its text and border in it and hovers with 5%, `subtle` draws its text in it and hovers with 12%, and `transparent` draws only its text in it, each mixed in OKLab toward transparent unless named otherwise. With a CSS colour, the `light` text is 70% of it toward the page's text. `autoContrast` is off unless given: the text on a solid shade is the palette's `contrast`, the same for `red` and `red.6`, and white for a colour that is no palette's; with `autoContrast`, the text is black or white, whichever contrasts more with the solid shade. The primary is a palette whose tokens, `--solix-color-primary-0` to `--solix-color-primary-contrast`, point at the primary palette, `blue`, on `:root` and `[data-color-scheme]`, and a theme's `primaryColor` re-points them; they are and read by every part that draws the primary, so a rule that sets them re-themes them all; a hand override sets every one of them, since one shade alone leaves the hover, the light variant and the text in the old primary. A CSS colour is a hex colour of 3, 4, 6 or 8 digits, a call of one of the colour functions of `src/css-colors.ts` spelled in lower case, or one of its colour keywords, the CSS named colours, `transparent` and `currentColor` as the list spells them; names are matched as written, not without regard to case as CSS does. `SolixColor` types the same forms, so the compiler refuses a typo such as `bleu`, `RGB(1 2 3)` and `#zzz`, but it checks only the first three digits of a hex colour, since a type of every count of digits is a union too large for the compiler, so `#12345` passes the compiler and falls back at run time. A value that is none of these, `inherit`, `Red` and a hex colour of 5 or 7 digits included, falls back to the primary palette; in the browser, Solid's development build warns of it in the console, and the server and a production build stay silent. A custom variant is a rule of the consumer's for its own `data-variant` value. `size` and `radius` are the component's variables, so a key reads its scale's token and a number is pixels in rem.
- The default look follows the visual reference: its page colours, its solid, hover and soft colours for the palettes it names, and the OKLCH utility palette it is built on for the others, its radii, sizes, shadows and type on the scales the props name. A few of its solid colours fall below 4.5:1 with their text, as `contrastExceptions` in `tests/support/contrast-exceptions.ts` lists; an app that needs AA there overrides those tokens, through the theme or on `[data-color-scheme]`. The contrast is promised only for the colours the library chooses: the default theme, and a palette named as `color`, such as `color="red"`, in every variant. A theme's `primaryColor` other than the default `blue` is the app's choice, so its contrast is the app's to check, as with a given colour; the demos in `apps` choose palettes whose solid shade meets 3:1 against the page in both schemes, which `tests/rules/demo-themes.test.ts` holds. A shade (`color="red.6"`) or a CSS colour (`color="#..."`) is painted with the mixes above whatever its contrast, which is then the app's to check; `contrastExceptions` never lists it.
- The modal's backdrop reads `--solix-color-backdrop` inside `::backdrop`, which inherits it from the dialog only in a 2024 engine: Chromium 122, Firefox 120 or Safari 17.4 or later.
- With a headless component library underneath, Solid's development build reported two diagnostics that could not be fixed from this side. On `<details>` it reports none.

## Not covered

- The stylesheet imported into a layer of the consumer's own, as `@import url(...) layer(vendor)` after the markup, together with a component that queries its container. The component's `<style>` orders a top-level `ui-sdk` and `solix` and adds its rules to `solix`, which ranks below `vendor`, so a container query's value loses to the component's default: a column given 6 of 12 takes its whole row. `apps/playground/tests/layer-order.test.ts` pins this.

- A consumer passing StyleX style objects, rather than the classes `stylex.attrs` compiles them to, to `class` or `classes`. `styles` takes inline declarations only.
- A precompiled entry for tools that do not know the `solid` condition
- Type declarations
- Installing the library from the registry
- A menu on the Popover API. A modal on `<dialog>` is built and checked in `apps/playground/tests/modal-protocol.test.ts`.
- A modal that is open when the page first loads. The server renders it closed, and it opens after hydration.
- `aria-invalid` on a text input. Its error look follows `:user-invalid`, and nothing mirrors that state to assistive technology yet.
- A style-prop value that holds a comment opener `/*` or an unclosed quote. It is kept, and in server-rendered markup it can hide the declarations that follow it in `style`, the consumer's included.
